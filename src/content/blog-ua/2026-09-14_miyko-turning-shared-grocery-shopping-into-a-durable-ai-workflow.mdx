MiyKo, або «Мій кошик», — це проєкт, який я зробив для українського AI-хакатону від Silpo.

У Silpo вже є AI assistant, який може додати товар у кошик, замінити його та допомогти із замовленням. Мені захотілося піти на один крок далі: перетворити взаємодію з одного prompt на shopping workflow для цілого household.

Не просто чат із магазином, а спільне замовлення, яке живе достатньо довго, щоб у ньому встигли взяти участь кілька людей.

## Ідея

Уявімо звичайну ситуацію:

- мама створила замовлення;
- тато додав кілька товарів;
- дитина попросила морозиво;
- система пам’ятає спільний контекст;
- водночас кожна людина може мати власні вподобання.

У такому сценарії AI вже не просто відповідає одному користувачу. Він координує людей, пам’ять, зміни у замовленні, погодження та зовнішнього provider.

Саме це стало основною ідеєю MiyKo.

## Чому household змінює продукт

Кошик для однієї людини — це відносно проста задача. Кошик для household потребує правил.

Хтось має бути власником замовлення. Інші учасники повинні бачити його, додавати свої побажання та розуміти, що вже змінилося. Деякі дії можна виконувати одразу, а деякі мають чекати на погодження.

Тому household у MiyKo — це не просто груповий чат. Це окрема boundary системи з учасниками, ролями, спільним контекстом і власним життєвим циклом замовлення.

## Memory, а не просто chat history

Мене цікавила не історія повідомлень сама по собі. Я хотів, щоб memory була керованою частиною продукту:

- її можна додавати;
- оновлювати;
- видаляти;
- відокремлювати спільний контекст household від особистого контексту учасника;
- не змішувати довготривалі вподобання зі станом одного активного замовлення.

Для цього я використав Mem0 для довготривалої household і member memory. Стан конкретного замовлення зберігається окремо в LangGraph, тому тимчасові рішення workflow не стають постійними “спогадами”.

Це важлива межа. Memory відповідає на питання «що система має пам’ятати надалі?», а workflow state — «де саме ми зараз у цьому замовленні?».

## Durable workflows після експерименту з Temporal

У попередньому проєкті Encois я експериментував із Temporal. У MiyKo мені хотілося спробувати іншу модель довгоживучого agent workflow через LangGraph і LangChain.

Замовлення не завжди завершується за одну сесію:

- хтось додає товар;
- інша людина змінює вибір;
- agent просить уточнення;
- provider тимчасово недоступний;
- товар потрібно замінити;
- через кілька годин workflow продовжується.

Тому agent має вміти зупинитися, зберегти стан і продовжити роботу після нової події.

У hackathon-версії локальний LangGraph checkpointer показує цю модель, але сам по собі ще не є production-grade durability. Для production я б додав надійне персистентне сховище, idempotency для provider calls, retries, timeouts та чіткі правила recovery.

## Невелика, але чітка архітектура

Я свідомо розділив систему на кілька boundary:

- React Native app відповідає за household, замовлення та approval UX;
- API перевіряє identity, membership і permissions;
- LangGraph керує станом і переходами workflow;
- LangChain з’єднує model з tools;
- Mem0 зберігає довготривалу memory;
- Silpo MCP виконує provider-specific дії.

API залишається security boundary. LangGraph координує замовлення, отримує потрібний контекст із Mem0 та використовує model, щоб обрати наступний крок. Якщо потрібні дані магазину або зміна кошика, workflow викликає Silpo через MCP. Результат повертається в LangGraph, зберігається у workflow state і стає наступним статусом у застосунку.

Таке розділення важливіше за кількість framework. Якщо permissions перевіряються лише в prompt або UI, це не security boundary. Якщо provider logic змішана з reasoning agent, її складніше замінити та відновити після помилки.

Токени provider також не повинні потрапляти в довготривалу memory. Вони потрібні тільки під час виконання конкретної дії.

## Providers після Silpo

Зараз у MiyKo реально інтегрований тільки Silpo. Але сама модель не повинна бути прив’язана до одного магазину.

Наступним кроком можуть бути АТБ, Glovo, delivery services або інші магазини. Household формулює потребу один раз, а provider layer вирішує, де і як її виконати.

Для цього потрібен спільний shopping contract і окремі adapters для кожного provider. Це дозволяє зберегти household workflow, навіть якщо API, каталог і checkout у кожного магазину різні.

## UI потрібно бачити

MiyKo має React Native app. Перша AI-generated версія UI була слабкою. Вона формально містила потрібні екрани, але не передавала сам продукт.

Я витратив ще кілька окремих сесій на переробку flow, hierarchy і станів. Це знову підтвердило простий патерн: UI потрібно бачити, а не тільки описувати.

Agent може виконати детальне текстове завдання і все одно створити інтерфейс, яким незручно користуватися. Screenshot або жива взаємодія дають feedback, якого немає в prompt.

## Models і cost

Я не намагаюся запускати кожну задачу на найдорожчій моделі.

Часто ефективніший процес виглядає так:

1. Дешевша модель робить першу версію.
2. Я дивлюся на результат.
3. Уточнюю справжню проблему.
4. Сильнішу модель використовую там, де дійсно потрібне reasoning.

Навіть дорогий agent може зробити неправильний UI. Тоді дорогі токени просто перетворилися на код, який доведеться видалити.

Cost optimization тут не означає завжди обирати найдешевшу модель. Воно означає використовувати сильну модель в точках, де її reasoning справді змінює результат.

## Що встигло в hackathon MVP

Hackathon змушує чесно визначити boundaries.

У MiyKo я сфокусувався на наскрізному flow: household, учасники, memory, planning, approval, Silpo OAuth, реальний кошик і передача користувача в checkout.

Це не готова multi-provider commerce platform. У production-версії ще потрібні надійніша durability, reconciliation з provider, спостережуваність, краща обробка конфліктів і adapters для інших магазинів.

Але MVP уже перевіряє головну ідею: AI shopping assistant може бути не одноразовою відповіддю, а спільним workflow, який пам’ятає контекст і переживає кілька людських рішень.

## Що я виніс

AI дуже добре робить implementation, коли ти вже розумієш system boundaries.

Але memory, workflows, UX і product behavior потрібно спочатку правильно сформулювати. Треба вирішити, що є довготривалою пам’яттю, хто може змінювати замовлення, коли потрібне погодження, що робити після помилки provider і де закінчується відповідальність продукту.

Інакше AI просто допоможе дуже швидко побудувати неправильну систему.
