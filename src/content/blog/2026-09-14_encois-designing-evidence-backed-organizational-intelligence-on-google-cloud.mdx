## 🤓 The idea

Encois is a small organizational intelligence system.

The easiest way to describe the idea is a mini-Palantir for companies: a system that connects information from different parts of a business and helps people understand what is happening.

Think about a company with 50–100 people. Its context changes all the time:

- a Jira issue becomes blocked;
- a pull request fails its checks;
- a deployment goes wrong;
- a customer sends an important email;
- a billing event changes;
- an internal decision affects a release.

None of these events means much in isolation. The useful context appears when they are connected.

A failed check may be related to a pull request. The pull request may block a Jira issue. The issue may belong to a release planned for Friday. The release may affect a customer commitment.

The question is not only, “What does this document say?”

It is:

> “What changed, why does it matter, and what needs attention now?”

That is the problem I wanted Encois to explore.

## 🤔 Why I did not want to build another RAG chatbot

The most obvious implementation would be to collect company documents, put them into a vector database and add a chat interface.

That can be useful, but it is not enough for this problem.

A company is not a static collection of documents. It is a changing system. Jira, GitHub, email, billing, deployments and internal tools continuously produce new events. The system needs to update its understanding when those events arrive.

Instead of importing everything into RAG once, Encois is designed around connectors, webhooks, source revisions and workflows.

I also did not want an AI that could simply invent a plausible story about the company.

The goal was to make every useful answer connected to:

- real events;
- authorized integrations;
- user permissions;
- known source data;
- workflow history;
- inspectable evidence.

In simple terms: less hallucination, more operational truth.

RAG can still be one part of the system. It can help retrieve relevant semantic context. But retrieval should not decide who can access data, whether a workflow completed, or whether an external action is allowed.

## 🔎 A simple example

Imagine a delivery manager asking:

> “Is this release still safe to ship on Friday?”

The answer may depend on open Jira work, GitHub pull requests, failed checks, deployment events and a document describing the release requirements.

An Encois workflow can collect those signals and produce three layers of output:

1. **Observed facts** — what Jira, GitHub and other Sources actually returned.
2. **Interpretation** — which blockers or dependencies the agent found across those facts.
3. **Recommendation** — what a person should review or decide next.

The recommendation should not hide the evidence behind it. A user should be able to see which issue is open, which check failed, where the information came from and when it was observed.

This is a small difference in the UI, but a big difference in the architecture. The system needs provenance, freshness, identity, scope and durable execution—not only a prompt and an answer.

## 🧠 I started with system design

Encois was a hackathon project built around Google Cloud and enterprise agents.

Before writing most of the application code, I spent several days thinking about the architecture.

I wanted to understand:

- which state belongs in PostgreSQL;
- which state belongs in Temporal;
- how Spanner Graph and Memory Bank should differ;
- where provider credentials should live;
- how company events should enter the system;
- how permissions should travel through long-running workflows;
- how agents should access tools;
- what should run on Cloud Run;
- how to make the whole path observable.

This was the most interesting part of the project for me.

The main architecture became:

```text
Company systems and events
  → Integrations and scoped Sources
  → TypeScript Gateway API
  → PostgreSQL control plane and transactional outbox
  → Temporal Coordinator and durable Workflows
  → Go Agent Runtime
  → private Agent Gateway
  → provider tools, Graph, Memory and artifacts
  → Google ADK and Gemini
  → evidence-linked result in the Dashboard
```

The important decision was not the number of services. It was giving each part one clear responsibility.

## 🧩 The main product concepts

I separated the product into a few concepts:

- **Integration** — a company-level connection to GitHub, Jira or another provider.
- **Source** — a specific repository, project, document or other scoped resource.
- **Source Revision** — an immutable version of the Source data.
- **Template** — a reviewed starting point for a workflow.
- **Blueprint** — the resolved and approved workflow definition.
- **Workflow** — a named process the company can run again.
- **Run** — one durable execution of that Workflow.
- **Evidence** — a reference supporting a fact or conclusion.

The path from an idea to execution looks like this:

```text
Template → Blueprint → Workflow → Run → Temporal execution
```

This may look like extra structure for a hackathon project. But it solves an important problem: a user can know exactly what was approved and executed.

If a Template changes tomorrow, an old Run still points to the immutable Blueprint used at the time. The system does not silently reinterpret its history using a new configuration.

## 📡 Events, connectors and changing context

An organizational intelligence system cannot depend only on manual questions.

Integrations connect Encois to company systems. Sources narrow those integrations to the resources a team is allowed to use. Webhooks and ingestion workflows bring new events and revisions into the platform.

The Source ingestion path is:

```text
authorize Integration
  → store a credential reference
  → register a scoped Source
  → create an immutable Source Revision
  → run ingestion in Temporal
  → extract facts and provenance
  → project organization context and agent memory
```

The raw artifact does not go into PostgreSQL or Temporal history. It belongs in Cloud Storage. PostgreSQL stores the Source, its scope, its revision and the reference to the artifact.

The ingestion workflow reads the artifact through the private Agent Gateway, normalizes it, extracts facts and keeps provenance. When the hosted data-plane adapters are enabled, those facts can be projected into Spanner Graph and relevant semantic context can be distilled into Agent Platform Memory Bank.

This keeps the original Source separate from derived context. A generated memory is useful, but it is not stronger evidence than the event or document it came from.

## 🔄 Temporal and durable execution

One thing I specifically wanted to practice was durable workflows.

I think durable execution will be very important for agent systems.

Agent work is often longer than one HTTP request. It may involve several tools, temporary failures, retries, external events, human approval or a pause until more information arrives.

For Encois, Temporal owns:

- long-running Workflows;
- retries and timeouts;
- pause and resume behavior;
- Signals from external events or people;
- state between execution steps;
- cancellation and recovery;
- durable execution history.

PostgreSQL does not try to reproduce this state machine. It stores the product-facing Run projection, evidence, actor, scope and audit data. Temporal remains the source of truth for execution.

### The organization Coordinator

Each organization has one long-lived Coordinator Workflow.

It receives versioned events such as:

- an Integration was connected;
- a provider changed;
- a Source became ready;
- a Workflow start was requested;
- a Workflow completed.

The Gateway writes the product state and an outbox event in the same PostgreSQL transaction. A dispatcher then delivers that event to the Coordinator with retries.

This avoids a common failure case: saving a Run in the database but losing the request before Temporal receives it.

For the hackathon version, the dispatcher runs inside the Gateway API. That keeps the first implementation small. Later it could move behind Pub/Sub or Kafka without changing the event contract or adding a second workflow engine.

### Generic Blueprint execution

The Go Runtime executes approved Blueprints through a generic Temporal Workflow.

A Blueprint can contain tool steps, agent steps, deterministic transforms, conditions, dependencies, timers and approval Signals. Independent ready steps can run in parallel.

The current implementation runs one approved Google ADK Agent Definition as one Temporal Activity. Temporal can retry that bounded unit, while model and tool calls stay outside deterministic Workflow code.

The trade-off is that internal agent turns have coarser visibility and retry behavior. A deeper Temporal/ADK integration could later make model calls and tool operations separate Activities, but that would need careful validation around determinism and dependency compatibility.

## 🤖 AI was not one unrestricted agent

The system does not give one agent every tool and ask it to operate the company.

An agent has a narrow role, typed input and output, an allowlist of tools, a timeout, a retry limit, a budget and an organization scope.

The deterministic parts stay in normal code:

- authentication;
- permissions;
- scope calculation;
- workflow transitions;
- schema validation;
- deduplication;
- approval rules.

Google ADK and Gemini are used for bounded reasoning and synthesis. The model can interpret evidence, but it cannot decide that a user belongs to another organization or that a failed workflow actually succeeded.

The Agent Gateway is the private boundary between the Runtime and company systems. It checks the service identity, signed execution capability, organization scope, policy version and requested tool. Provider credentials are resolved through Secret Manager and never returned to the browser, model or Temporal history.

Tools are read-only by default. If Encois later writes to Jira, GitHub or another external system, that action needs a separate permission, approval, audit, idempotency and recovery path.

A recommendation is not an automatic action.

## ☁️ What each Google Cloud service owns

I did not want to use Google Cloud services only to make the architecture diagram look impressive. Each one needed a clear reason to exist.

### Cloud Run

The hosted deployment target uses Cloud Run for the Dashboard, Gateway API, Agent Runtime and private Agent Gateway.

This keeps the services independently deployable without introducing Kubernetes for the first version. Cloud Run IAM can protect service-to-service calls, while Encois still applies its own application-level capability and scope checks.

Cloud Run Jobs are intended for explicit operations such as database migrations, retention and demo seeding. Restarting an application service should never recreate or modify product data automatically.

### Cloud SQL for PostgreSQL

PostgreSQL is the control plane.

It stores users, memberships, organization units, permissions, Integrations, Sources, Blueprints, Runs, outbox rows and audit-friendly projections.

The API runtime uses a restricted connection. Database migrations use a separate operator connection. The Go Runtime and Agent Gateway do not connect directly to the control-plane database.

### Cloud Storage

Cloud Storage owns large raw Source artifacts. Temporal receives only references and scope information, not full documents or provider credentials.

### Spanner Graph

Spanner Graph is the target Organization Memory store for structured company facts and relationships.

This is different from putting text chunks into a vector database. The long-term idea is to connect projects, teams, people, systems and operational events while keeping provenance.

The current implementation is still early. It projects scoped fact nodes with provenance, but rich entity normalization and relationship edges are future work.

### Agent Platform Memory Bank

Memory Bank stores agent-specific semantic context. It can help retrieve or distill useful information between workflows.

It is not the company source of truth, the permission system or the durable workflow state. Those boundaries stay separate.

### Vertex AI and Gemini

The Go Runtime uses Google ADK and Gemini for reasoning and synthesis. The repository currently defaults to `gemini-3.7-flash`, while the deployed model and thinking level remain environment configuration.

Gemini receives validated, scoped inputs. It does not receive unrestricted database access or provider credentials.

### Secret Manager, Logging and Trace

Secret Manager owns provider credentials and service secrets.

Cloud Logging, Cloud Trace and OpenTelemetry-compatible instrumentation make the workflow inspectable across the Gateway, Temporal execution, Runtime and private tool calls.

The system records events, timing, retries, evidence reads and error classes. It does not need to store hidden reasoning, full prompts, raw documents or tokens in logs.

## 🔐 Permissions have to survive the whole workflow

Organization is the hard tenant boundary in Encois.

Inside an organization, access may follow a hierarchy:

```text
Organization → Department → Team → Project → Person / System
```

The Gateway calculates the effective scope from the authenticated membership and selected unit. But checking permission only at the first HTTP request is not enough.

The same organization, scope, actor and capability information travels through the outbox, Temporal Workflow and private tool requests. The Runtime and Agent Gateway check it again at their own boundaries.

This matters because a workflow may continue long after the browser request has ended. A model-generated organization ID must never become authorization just because it appeared inside a payload.

The system also fails closed. Missing or unknown data is not converted into a convenient successful state. A missing onboarding record is an error. An unknown Run status is a contract mismatch. A provider authentication failure remains visible as degraded or requiring reauthorization.

## 🧑‍💻 Using AI to build outside my main stack

There was another AI lesson inside this project.

I do not normally write Go. But Go was the practical language for parts of the Google integration, the Temporal worker and the agent runtime.

AI wrote much of that part. I reviewed the code, checked it against the documentation and used the surrounding tests and contracts to validate the boundaries.

This is a good example of where AI changes software development for me. I could work outside my main stack without first spending several weeks learning enough Go to build the first version alone.

That does not mean blindly trusting generated code. The useful workflow was:

1. Define the architecture and contracts first.
2. Give the coding agent one bounded area.
3. Review the result against the intended boundary.
4. Compare unfamiliar SDK usage with official documentation.
5. Keep cross-language communication behind versioned schemas.

I also split the wider project work across different AI agents for the API, AI runtime, documentation, infrastructure, diagrams, testing and bug fixing.

This worked because the system already had clear boundaries. The API agent did not need to understand every detail of Spanner. The infrastructure agent could work from explicit service responsibilities. The Go and TypeScript sides met through OpenAPI and JSON Schema rather than shared assumptions.

The same principle applied both to the product and to building it: specialized agents are more useful when their scope is clear.

## 🖥️ The UI lesson

The Dashboard turned out well for a developer and hackathon demo.

It exposes Integrations, Sources, Templates, Blueprints, Workflows, Runs, events, permissions and memory. That is helpful when demonstrating that the backend is real and when debugging the system.

But it also revealed a product problem: the Dashboard was becoming a beautiful interface to the database.

A real user should not need to understand every internal resource before Encois becomes useful.

The product should move toward one operational picture that answers:

- What changed?
- What needs attention?
- Which release is blocked?
- Which Workflow should run?
- What has already been checked automatically?
- Which conclusion needs a human decision?

That is a better product direction than ten pages of technically correct data.

The underlying control plane is still necessary. Integrations, Sources, permissions and workflow definitions need somewhere to be managed. But they should support the intelligence experience rather than become the main experience.

## 🧪 Local demo and current limits

The local environment keeps the same application topology using Docker Compose, PostgreSQL, Temporal, Auth and Storage emulators, the Dashboard, Gateway, Runtime and Agent Gateway.

It creates a synthetic company called `Sun Inc` with real control-plane records and Temporal-backed Runs. Provider fixtures and infrastructure mocks are explicit adapter modes; the browser does not invent users, permissions or completed workflows.

Real Gemini, Spanner Graph and Memory Bank integrations are opt-in because they require configured Google Cloud resources and can incur cost.

The project is still a hackathon MVP. Some important work remains:

- richer Graph entities and relationships;
- production validation of hosted IAM, retention and cost;
- hardened provider authorization and lifecycle behavior;
- independent outbox delivery at larger scale;
- more granular Temporal/ADK execution;
- stronger deployment and disaster-recovery processes;
- an intelligence-first product UI.

I prefer keeping these limitations visible instead of describing planned architecture as a finished enterprise platform.

## 🚀 Where Encois could go next

The next version should not start by adding more pages or giving the agent more tools.

It should make the operational picture smaller and more useful.

Encois could prepare scheduled briefings, detect meaningful changes and suggest investigations before a user asks. A conversational or voice interface could help people explore evidence without replacing the same identity, scope and audit boundaries.

Agents could also propose new Sources, Blueprints or workflow configurations based on organization context. Those proposals should remain reviewable and require the appropriate permission before becoming active.

External actions may eventually be useful, but only as explicit capabilities. An agent that can create a Jira issue or change a deployment needs a much stronger approval and recovery model than an agent that recommends the action.

## 📚 Conclusion

Encois started from a simple idea: company context is always changing, and useful organizational AI has to change with it.

The hard part is not connecting Gemini to a set of documents. It is building a system that knows:

- what happened;
- where the information came from;
- who is allowed to see it;
- which workflow produced the result;
- what is fact, inference or recommendation;
- what still needs a human decision.

Temporal gave me a practical way to explore durable agent workflows. Google Cloud provided separate places for runtime services, control-plane data, raw artifacts, structured organization context, semantic memory, secrets and model execution. AI coding agents helped me build parts outside my normal stack, especially Go.

The biggest product lesson came from the UI: users do not need another database browser. They need one clear operational picture of what changed and what deserves attention.

That is what I want Encois to become.
