## 🤓 I wanted a fasting tracker for myself

The idea behind Simple Fasting was very simple.

I wanted a fasting tracker that I could open, start or stop a fast, and close.
No backend. No tracking. No account. No subscription popup every time I opened
the app.

Privacy was not something I planned to add later. It was part of the product
idea from the beginning. Fasting history, goals, notes, and reminders should
stay on the device unless the user explicitly exports them.

The final project became more than a timer. It now has local history and
statistics, reusable goals, reminders, import and export, iOS and Android
widgets, an optional iOS Live Activity, and a small website.

But the product was never supposed to become large. The goal was still to make
one simple action feel calm and reliable.

![Simple Fasting ready and active fasting screens in light and dark themes](/images/blog/building-simple-fasting-with-ai-agents/01-fast-screens.png)

I used AI agents for most parts of the work: product thinking, system design,
React Native code, tests, UI iterations, documentation, and release setup.
This made development fast, but it also created new problems. When code becomes
cheap to produce, it becomes very easy to produce too much of it.

This article is about that process: what worked, where I overdid it, and what I
would do differently next time.

## 🧭 I was doing spec-driven development before calling it that

Before building many features, I started writing documents.

The repository had a `docs/` directory with:

- an initial product requirements document;
- architecture notes;
- feature descriptions;
- separate documents for important systems;
- data behavior;
- edge cases;
- release requirements.

At the time, I did not think much about the term *spec-driven development*. I
just wanted the decisions to exist somewhere outside my head and outside an AI
chat.

That became one of the best decisions in the project.

An agent can work well inside one task, but the next task may start with a new
context. If important decisions exist only in a conversation, the agent has to
guess them again. Sometimes it guesses differently.

The documents gave every new task the same starting point:

- what the product does;
- what it intentionally does not do;
- where data lives;
- which part of the code owns each behavior;
- what should happen when something fails;
- how a change should be verified.

The most useful part was documenting non-goals. If I only asked AI to build “a
modern fasting app,” it could reasonably add authentication, cloud sync,
subscriptions, analytics, or a large state-management system. Those features
are common in similar products, but they were wrong for mine.

A written product boundary made it easier to reject code before it became part
of the architecture.

## 🗂️ Documentation became the shared memory

Simple Fasting has several connected surfaces:

```text
app/
  Expo and React Native application

www/
  static Astro website

docs/content/
  Privacy Policy, Terms, FAQ, and What's New

docs/dev/
  product, release, and future-scope documents
```

They are currently in one repository, but I treat them as separate ownership
areas. The same approach works when an application is split across multiple
repositories.

Every shared concept needs one source of truth. Legal and help content is
written once and synchronized into the app and website. History is the source
of truth for statistics. The app, widgets, and Live Activity should share the
same fasting model instead of calculating the same state in different ways.

This matters even more with several AI agents. Two agents can both write valid
code and still create two different versions of the product. Clear ownership
prevents that.

For me, good project documentation is not a large description of every file.
It records decisions that should survive between tasks.

Code shows what exists now. Documentation explains what must remain true while
the code changes.

## 🤖 My AI workflow

I did not start by asking AI to build the complete application.

First, I generated wireframes and mockups. I looked at other fasting apps,
compared their flows, and changed the ideas to fit what I wanted. Then AI helped
turn those decisions into React Native screens and working behavior.

The loop was usually:

> describe a small part → implement it → run the app → use the screen → explain
> what feels wrong → adjust it

I used different agent roles during that process.

An architecture-focused agent helped think through storage, state ownership,
notifications, widgets, and failure behavior. An implementation agent worked on
a defined feature. A UI-focused pass reviewed screenshots and the running app.
A verification pass checked tests, types, builds, and whether the result still
matched the specification.

These did not always need to be different models or permanent agents. The
important part was giving each task a clear role, context, boundary, and
definition of done.

For example, “add an end-of-fast reminder” is too vague. A useful task also
needs to say:

- the reminder is local;
- it belongs to the current active fast;
- changing or ending the fast must update it;
- notification failure must not block the timer;
- permission behavior must be checked on the platform;
- storage and restoration need tests.

That gives AI space to implement the feature without asking it to invent the
product rules.

## 🧠 I did not use the strongest model for everything

I often started with a simpler model for focused work. It was enough for small
components, tests, direct refactors, and changes that followed an existing
pattern.

I moved to a stronger model when the task involved architecture, several parts
of the product, native platform behavior, or a UI problem that was difficult to
describe.

This was partly about quality and partly about tokens.

A stronger model with too much context can spend a lot of tokens exploring the
wrong direction. A smaller model can work very well when the specification,
files, and expected result are clear.

The useful rule was not “always start cheap” or “always use the best model.” It
was:

> Use stronger reasoning when the uncertainty is expensive.

I could use a stronger model to define an architecture, a simpler one to
implement a narrow part, and a stronger one again only if review found a deeper
problem.

Keeping stable decisions in the repository also reduced repeated context. I did
not need to explain privacy, product scope, or storage ownership from zero in
every prompt.

## ⚠️ Where I overengineered the app

AI can write another safety path in a few minutes. That makes every additional
layer feel cheap.

During development, I added things such as:

- retries;
- retry counters;
- hard reset flows;
- rollback-like behavior;
- import and export;
- extra recovery paths for local data.

Some of this is useful. Local data should not be treated carelessly, especially
when there is no backend copy. Import and export also support the product's idea
of user-owned data.

But part of the implementation was too much for that stage of the product.

The problem was not that the code was technically wrong. The problem was that I
was designing recovery systems before the core product had enough real use to
justify all of them.

AI makes it easy to confuse “we can add this” with “the product needs this.”

Every extra path creates more states, tests, copy, and maintenance. A retry
needs failure rules. A hard reset needs warnings and confirmation. Rollback-like
logic needs a clear idea of what is atomic. Import and export need validation,
conflict handling, and privacy explanations.

The implementation cost may be small. The product cost remains real.

If I started again, I would ask three questions before adding a safety system:

1. Which real failure does this handle?
2. Can the user recover without it at this stage?
3. How many new states will it add to the product?

That would have kept the first version smaller.

## 🎨 My second mistake was delaying the design system

I did not create a proper design system early enough.

AI produced screens quickly, and each screen looked reasonable on its own. Over
time, however, similar parts became slightly different:

- components were duplicated;
- spacing was repeated instead of shared;
- similar screens used different structures;
- button and surface styles slowly drifted;
- the code became larger than the product needed.

This is a common AI UI problem. The model solves the current screen. It does
not automatically protect consistency across the whole application.

At some point, I stopped feature work for about two days and cleaned it up. I
created reusable components, established clearer primitives, aligned the
styles, and effectively built a small design system.

![Simple Fasting settings screens showing shared controls and theme behavior](/images/blog/building-simple-fasting-with-ai-agents/02-settings-screens.png)

That cleanup changed later work. Instead of describing every visual property, I
could tell an agent to reuse the existing screen shell, section surface, button,
heading, spacing, and theme tokens.

The design system became a shared language between me and AI.

It also reduced context. “Use the standard section surface” is more precise and
cheaper than repeatedly describing padding, border, radius, colors, dark mode,
and interaction states.

For an AI-built interface, I would now establish these things early:

- semantic colors for light and dark themes;
- a small spacing and radius scale;
- typography and numeric styles;
- shared buttons, rows, surfaces, headings, and feedback states;
- rules for safe areas, tabs, and stack screens;
- a preference for native controls when the platform already has the right
  interaction.

The goal is not to design every screen in advance. It is to give every screen
the same visual grammar.

## 📱 UI cannot be completed inside a specification

Functional behavior can often be planned in detail before implementation.

UI and UX are different.

You can describe a screen, make a wireframe, define components, and specify its
states. But you still need to open it and use it. The balance, density, touch
targets, keyboard behavior, safe areas, native navigation, and small platform
differences only become clear in the running product.

If you give AI one huge UI specification and wait until the whole application
is finished before opening it, you will probably delete and rebuild a lot of
work.

The better loop is short:

> build → look → adjust → continue

I used the browser for the website and public content. I used computer-use tools
to navigate interfaces and check real interactions. For the mobile app, I used
the iOS Simulator and Android emulator to inspect every screen manually.

This exposed problems that code review could not:

- content hidden by a native tab bar;
- unnecessary scrolling on a normal phone;
- keyboard overlap;
- incorrect picker behavior;
- inconsistent light and dark themes;
- navigation that felt wrong on one platform;
- components that looked reusable in code but behaved differently on screen.

Screenshots helped, but they were not enough. A screenshot can show hierarchy,
spacing, and alignment. It cannot show what happens after a tap, how the
keyboard changes the layout, or whether state survives reopening the screen.

When I gave feedback to AI, concrete descriptions worked much better than
general reactions.

“This screen feels wrong” is weak feedback.

“The Start button is hidden behind the tab bar on the smallest iPhone size” or
“the selected goal returns to the previous value after reopening the tab” gives
the agent a state, an action, and a visible failure.

## 🧪 The simulator is feedback, not proof of a release

I also separated fast iteration from full verification.

Running a complete native build after every small UI change is slow. During
iteration, I used the narrowest useful check, opened the app in a simulator,
and inspected the changed flow.

Broader checks came when the feature slice was stable:

- TypeScript;
- unit and integration tests;
- iOS and Android bundle exports;
- native builds when platform code changed;
- physical-device checks for notifications, widgets, Live Activity, and release
  behavior.

The simulator made feedback fast, but it did not replace builds, signing, or
device testing. The opposite was also true: a successful build did not mean the
interface was good.

I stopped accepting phrases such as “this should work” or “the build should
pass” as evidence. AI can explain its expectation. The tool or device has to
confirm it.

The practical loop became:

> implement → run a narrow check → use the UI → report the exact problem → fix
> it → run the broader gate when the feature is stable

## 🧱 Build features as complete slices

Another useful change was thinking in user outcomes instead of files or isolated
screens.

A fasting flow touches several parts of the system:

```text
Choose a goal
  → persist the selection
  → start a fast
  → calculate elapsed and remaining time
  → update widgets and Live Activity
  → end the fast
  → save it to History
  → update statistics from History
```

If separate agents build the timer, History, and widget independently, they may
create different models of the same fast. A vertical slice exposes those
differences early.

![Simple Fasting statistics and history screens using the same session data](/images/blog/building-simple-fasting-with-ai-agents/03-data-screens.png)

The same applies to documentation. Editing the Privacy Policy is only the first
step. The complete slice includes synchronization, the local app screen, the
website route, and a check that catches stale content.

The unit of work should be a verified outcome, not a file.

## 🧩 What I would do next time

My process would be:

1. Write the product goal, non-goals, privacy boundary, and core data model.
2. Define ownership between the app, website, shared content, and native
   features.
3. Create a small design system before building many screens.
4. Use wireframes to choose direction, not to finalize every detail.
5. Give each agent a clear role, context, boundary, and definition of done.
6. Use stronger models for uncertainty and simpler models for bounded work.
7. Build one complete user flow at a time.
8. Open the product after every meaningful UI change.
9. Add recovery logic only for failures the current product genuinely needs.
10. Keep documentation updated so the next agent starts from current decisions.

The biggest change is that I would separate two kinds of planning.

For architecture, data, and functional behavior, I would plan early and write
clear specifications.

For UI, I would define the system early but discover the final screens through
short feedback loops.

## ✨ Conclusion

Simple Fasting started as a small tool I wanted for myself. AI helped me build
it much faster than I could have alone, including parts that required native
mobile code, platform testing, and repeated UI work.

It also made overengineering easier. More code was always one prompt away.

The project taught me that AI works best when the product has stable memory and
fast feedback. Specifications preserve decisions. Architecture defines
ownership. A design system keeps generated UI consistent. Browser and simulator
use show what the code actually became. Tests and builds check claims that a
model cannot prove by itself.

For functional systems, plan more before coding.

For UI, create the rules first, then work in short cycles:

> build → look → adjust → continue

That balance helped Simple Fasting stay close to the original idea: a small,
private app that does one job without turning the user into the product.
