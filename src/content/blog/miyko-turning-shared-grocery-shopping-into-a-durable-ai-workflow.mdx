## 🤓 The idea

I built MiyKo for the AI Factory by Silpo hackathon.

Silpo already has an AI assistant that can help with shopping: find a product, add something to the basket, replace an item and continue toward checkout.

My idea was to go one step further.

Instead of building another assistant around one prompt and one person, I wanted to build a shopping workflow for a **household**.

The difference sounds small, but it changes the whole system.

A normal assistant can answer:

> “Add ice cream to my basket.”

A household workflow needs to handle a longer story:

- one person creates the order;
- another person adds something later;
- a child asks for ice cream;
- the owner approves or declines that request;
- the system remembers shared preferences;
- every person can also have personal context;
- the real basket may change several hours after the first message.

At that point, it is no longer only a chat. It is a process with people, roles, memory, state and external providers.

That was the main experiment behind MiyKo.

## 🏠 Why household changes the product

The household can be a family, one person or a temporary group. The same model can work for an office lunch, a party or a picnic.

Imagine a simple dinner:

1. Mom starts the order.
2. Dad adds drinks.
3. A child asks for ice cream.
4. The child’s request waits for approval.
5. The family confirms the plan.
6. MiyKo prepares the real store basket.

Everyone works with the same workflow, but not everyone has the same permissions.

In the MVP, an owner or admin can approve requests and perform provider actions. An editor can add to the shared plan. A viewer can make a request, but it must be approved before it affects the real basket.

This is important because the AI does not decide who has authority. The API knows the authenticated member and their role. A prompt cannot turn a viewer into an owner.

## 🧭 The complete MiyKo flow

The demo follows one shared order from the first request to the Silpo checkout.

### 1. One workflow keeps the process together

The MVP uses one workflow kind called `step-order`. LangGraph keeps the active state, pauses when a decision is needed and resumes the same workflow later.

![MiyKo step-order workflow graph](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/01-langgraph-step-order-graph.png)

This graph is not only a chain of AI calls. It represents the real lifecycle of the order: planning, member changes, approvals, provider actions and completion.

### 2. Different people see the same order

Each household member has a separate authenticated session. They do not share login credentials, but they can see the same active workflow.

![MiyKo owner and viewer dashboards](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/02-dual-user-empty-dashboard.png)

The household screen shows members, roles and the connected provider. The owner connects Silpo once for the whole household.

![MiyKo household members and connected provider](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/03-household-members-and-provider.png)

Other members can use that connection through the workflow, but they never receive the provider token.

### 3. Silpo stays a separate trusted system

The owner connects Silpo through OAuth 2.1 with PKCE. Authentication happens on the Silpo side, so MiyKo never asks for the owner’s store password.

![Silpo OAuth authorization for MiyKo](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/04-silpo-oauth-authorization.png)

The credentials remain encrypted on the backend. When the workflow needs to call Silpo MCP, the API passes the access token as runtime-only context. It is not stored in the mobile app, LangGraph state or memory.

### 4. Previous purchases become useful memory

Before starting the first order, the owner can import a summary of recent Silpo receipts.

![Recent Silpo purchases stored as MiyKo memory](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/05-mem0-order-history-memories.png)

This gives MiyKo context such as products the household bought before or choices that may be useful again.

![MiyKo household memory in Mem0](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/13-mem0-memory-dashboard.png)

Memory helps the agent make a better suggestion. It does not give permissions and it does not replace the current provider data.

### 5. The plan exists before the real basket

The owner starts a dinner workflow in the React Native app.

![Owner starting a dinner workflow in MiyKo](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/06-owner-order-dashboard.png)

MiyKo reads relevant memory and creates the initial shared plan. At this point, the Silpo basket is still untouched.

![Initial shared dinner plan in MiyKo](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/07-step-order-initial-plan.png)

I wanted planning and execution to be separate. During planning, people can speak naturally, add ideas and change their minds. Before execution, the system must check the actor, permissions and current provider state.

### 6. The workflow pauses for approval

When a viewer asks to add ice cream, the request remains in the same workflow and waits for an owner or admin.

![Household request and owner approval in MiyKo](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/10-household-approval-flow.png)

After approval, LangGraph resumes the same thread. The context is not copied into a new chat and the order is not recreated from scratch.

### 7. The agent prepares a real basket

Only after the household agrees on the plan does an authorized member ask MiyKo to prepare the basket.

The workflow discovers the current Silpo MCP tools, resolves products and updates the real provider basket. Product names, images, prices and totals come from Silpo, not from a local MiyKo catalog.

![Real Silpo basket prepared through MiyKo](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/08-silpo-basket-ready.png)

The workflow also writes structured logs for model calls, MCP discovery and provider actions. Credentials, prompts and raw sensitive arguments are not logged.

![Silpo MCP actions in the MiyKo workflow logs](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/09-silpo-mcp-workflow-logs.png)

### 8. Checkout still belongs to Silpo

Silpo MCP can work with the basket and return a checkout link, but it does not expose a final place-order tool. MiyKo prepares the basket; the owner finishes the purchase in Silpo.

![Silpo checkout basket prepared by MiyKo](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/11-silpo-checkout-basket.png)

That boundary is intentional. MiyKo must not say that an order is complete when it only has a basket and a checkout URL.

![Completed MiyKo workflow on two household dashboards](/images/blog/miyko-turning-shared-grocery-shopping-into-a-durable-ai-workflow/12-completed-order-dashboard.png)

The screenshot shows a completed MiyKo workflow. The final provider confirmation still happens in Silpo.

## 🧠 Memory, not chat history

I was not interested in storing a long chat transcript and calling it memory.

I wanted memory to be managed:

- add useful memories;
- update them when preferences change;
- remove them when they are wrong or no longer relevant;
- keep shared household memory;
- keep personal member context;
- keep order-specific state inside the active workflow.

These are different things.

Mem0 stores long-term household and member memory. LangGraph keeps the transient context for the current order. PostgreSQL does not duplicate either one.

For example, “the household often buys food for two days” can be long-term memory. “Add ice cream to tonight’s order” belongs to the active workflow. The current ice cream price still belongs to Silpo.

This separation also protects the permission model. Memory may say that a child likes ice cream, but it cannot approve the purchase. The API still checks the real member role.

## 🔄 Durable workflows after experimenting with Temporal

In another project, Encois, I experimented with Temporal for durable workflows.

With MiyKo, I wanted to explore a different model: a long-running workflow built around an AI agent and LangGraph.

A shopping order may live much longer than one request:

- someone adds an item;
- another person changes it;
- the agent asks a question;
- a provider is temporarily unavailable;
- a product needs replacement;
- several hours later, the workflow continues.

This is why a simple request-response API is not enough. The process needs a stable identity and state that can pause between actions.

MiyKo creates one workflow UUID and reuses it as the LangGraph thread ID. The workflow can then resume from the same point instead of trying to reconstruct the order from chat messages.

For reliable delivery, API actions go through an outbox worker. Temporary failures can be retried with an idempotency key, while business decisions such as “declined by owner” stay final.

The local LangGraph Agent Server was enough for the hackathon demo. It keeps development checkpoints across ordinary local restarts while its storage is preserved. A production version would need stronger durability guarantees for machine loss and deployment replacement.

## 🧩 Keeping the architecture small

MiyKo has five main runtime boundaries:

- **Expo / React Native** for the mobile experience;
- **Hono API** for authentication, household roles and provider connections;
- **LangGraph** for the active workflow and pause/resume state;
- **Mem0** for long-term household and member memory;
- **Silpo MCP** for current products, basket operations, fulfillment and checkout.

The API is the security boundary. LangGraph coordinates the order, reads relevant context from Mem0 and uses the model to choose the next step. When that step needs store data or a basket change, it calls Silpo through MCP. The result returns to LangGraph, is saved in the workflow state and becomes the next status shown in the app.

PostgreSQL is a small control plane. It stores users, households, roles, provider bindings, workflow references, approval decisions, audit records and outbox state.

It does not store a second product catalog, a second basket or a copy of LangGraph checkpoints.

This was an important decision. Creating tables for everything would make the system look complete, but it would also create difficult questions:

- Which price is correct when Silpo changes it?
- What happens when a locally stored product becomes unavailable?
- Which copy of the basket is the source of truth?
- How do two workflow states stay synchronized?

The simpler answer is to leave provider data with the provider, workflow state with LangGraph and reusable memory with Mem0.

## 🔌 Providers beyond Silpo

Silpo is the only implemented provider in the MVP, because this was a Silpo hackathon and I wanted one real end-to-end integration.

But the household workflow should not depend on one store forever. The longer-term direction can include:

- ATB;
- delivery providers;
- Glovo;
- other grocery stores;
- a workflow that compares several baskets before the household chooses one.

That is why provider authentication and MCP integration sit behind a separate boundary. Adding a new store should not require rebuilding household membership, approvals or memory.

## 📱 The UI lesson

I built the client as a React Native app.

The first AI-generated UI was weak. The functionality was there, but the product did not feel clear. I spent several separate sessions reviewing and rebuilding the screens.

It confirmed the same pattern I have seen in other projects:

> You need to see UI, not only describe it.

An agent can generate a screen from a prompt, but it cannot replace visual judgment. You still need to open the product, follow the flow, notice what is confusing and give concrete feedback.

For MiyKo, this mattered because the UI had to explain several states without exposing internal architecture: who is acting, what is waiting for approval, whether the basket is only planned or already prepared, and what the user should do next.

Those details are difficult to solve in one prompt. They become clear through iteration.

## 💸 Models and cost

I do not try to run every task on the most expensive model.

A more practical workflow is often:

1. A cheaper model creates the first version.
2. I look at the actual result.
3. I understand the problem more clearly.
4. I use a stronger model where reasoning is really needed.

This is especially important for UI work. Even an expensive agent can build the wrong interface. If I did not inspect the direction early, I would simply spend more tokens on code that I later delete.

Model choice does not replace good task decomposition. A strong model is most useful when the problem requires it, not when the prompt is still vague.

## ⚖️ What belonged in the hackathon MVP

I focused on one complete scenario:

- connect a real Silpo account;
- load recent purchase context;
- create a shared dinner workflow;
- let another member add a request;
- pause for approval;
- prepare a real basket;
- return the Silpo checkout link.

Notifications, recurring orders, multi-store comparison and production deployment are natural next steps, but they were not required to prove the idea.

For an AI prototype, one real end-to-end flow is more valuable than a large feature list built around mocked integrations.

## 📚 What I learned

AI is very good at implementation when you already understand the system boundaries.

But memory, workflows, UX and product behavior need to be described correctly first. Otherwise, you can build the wrong system very quickly.

For MiyKo, the most useful decisions happened before the final implementation:

- a household owns the shared process;
- the workflow survives between messages;
- memory is managed context, not authority;
- the API owns identity and permissions;
- the provider owns current products and the real basket;
- important actions stay under human control.

The grocery use case is only one example. The same pattern can work for travel planning, office procurement, support workflows or any agent that helps several people prepare a real external action.

The main value of the agent is not that it can call many tools. It is that it can coordinate context across people and systems while knowing where its authority ends.
